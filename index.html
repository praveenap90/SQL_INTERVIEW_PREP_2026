📌 FUNDAMENTALS

SELECT Fundamentals ▸

Concepts: SELECT, FROM, WHERE, ORDER BY, LIMIT, DISTINCT

Real-world example: Fetching top 10 customers by revenue with filters and sorting.

SELECT customer_id, SUM(amount) as total
FROM orders
WHERE amount > 100
GROUP BY customer_id
ORDER BY total DESC
LIMIT 10;
💡 Always use LIMIT in early query development to avoid returning millions of rows.

Interview tip: Emphasize the importance of filtering early (WHERE clause) to reduce dataset size before aggregation.

🐍 SQL vs. Pandas Quick Reference

JOINs & Table Relationships ▸

Concepts: INNER JOIN, LEFT/RIGHT/FULL OUTER JOIN, CROSS JOIN, Self-joins

Join types in order of frequency: INNER (most common), LEFT, RIGHT, FULL OUTER, CROSS (least)

SELECT o.order_id, c.customer_name, p.product_name
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id
LEFT JOIN products p ON o.product_id = p.product_id;
💡 LEFT JOIN preserves all rows from the left table, filling NULLs for missing matches.

Interview tip: Be ready to explain the difference between INNER and LEFT JOIN with a concrete example (e.g., all customers vs. only those with orders).

📋 JOIN Decision Table

Scenario Use This Join Why
Only matching rows from both tables INNER JOIN Removes non-matches (default, fastest)
All from left, matches from right LEFT JOIN Keep incomplete records from left
All from both, with NULLs for non-matches FULL OUTER JOIN Union of both sides
All combinations (Cartesian product) CROSS JOIN Rare; useful for generating dates or sequences
Aggregation & GROUP BY ▸

Concepts: GROUP BY, HAVING, aggregate functions (COUNT, SUM, AVG, MIN, MAX)

Common pattern: GROUP BY non-aggregated columns, filter groups with HAVING, not WHERE.

SELECT category, COUNT(*) as product_count, AVG(price) as avg_price
FROM products
GROUP BY category
HAVING COUNT(*) > 5
ORDER BY avg_price DESC;
💡 HAVING filters on aggregated results; WHERE filters on individual rows.

Interview tip: Explain why WHERE can't filter on aggregates — the aggregate hasn't been computed yet at the WHERE stage.

📊 Aggregate Function Quick Reference

Function Purpose Example
COUNT(*) Count all rows COUNT(*) = 150 (includes NULLs)

🔄 ADVANCED PATTERNS

Subqueries & CTEs ▸

Concepts: Scalar subqueries, correlated subqueries, IN/EXISTS, Common Table Expressions (CTEs)

CTEs are more readable: WITH clauses make complex logic clearer.

WITH high_value_orders AS (
  SELECT customer_id, COUNT(*) as order_count
  FROM orders
  WHERE amount > 500
  GROUP BY customer_id
)
SELECT c.customer_name, hv.order_count
FROM customers c
JOIN high_value_orders hv ON c.customer_id = hv.customer_id;
💡 Use CTEs for readability; use subqueries in SELECT for single-value lookups.

Interview tip: Prefer CTEs over nested subqueries in real-world code — they're easier to test and reuse.

📋 Real-World Scenarios

Scenario 1: Top-N Records per Group (Window Function)
Approach SQL Example Why / When to Use
CTE + Window (BEST) WITH ranked_rows AS (SELECT *, ROW_NUMBER() OVER (PARTITION BY category ORDER BY amount DESC) AS rn FROM table_name) SELECT * FROM ranked_rows WHERE rn <= 3; Clean, scalable, interview-favorite
Temporary Table CREATE TEMPORARY TABLE temp_ranked AS SELECT * FROM table; SELECT * FROM temp_ranked WHERE rn <= 3; Best for reuse across queries
Subquery SELECT * FROM table_name t WHERE amount >= (SELECT MIN(amount) FROM (...) LIMIT 3); Hard to read, inefficient
Scenario 2: Running Total (Window Function)
Approach SQL Example Why / When to Use
CTE + Window (BEST) WITH running_total AS (SELECT date_col, amount, SUM(amount) OVER (ORDER BY date_col) AS cumulative_amount FROM table_name) SELECT * FROM running_total; Analytics & reporting
Temporary Table CREATE TEMPORARY TABLE temp_running_total AS SELECT date_col, SUM(amount) OVER (ORDER BY date_col) FROM table_name; Large datasets
Subquery ❌ Not practical Avoid
Scenario 3: Deduplication (Advanced)
Approach SQL Example Why / When to Use
CTE + Window (BEST) WITH ranked_rows AS (SELECT primary_key, ROW_NUMBER() OVER (PARTITION BY key_column ORDER BY primary_key) AS rn FROM table_name) DELETE FROM table_name WHERE primary_key IN (SELECT primary_key FROM ranked_rows WHERE rn > 1); Safe & scalable
Temporary Table CREATE TEMPORARY TABLE temp_dupes AS SELECT primary_key FROM (...) x WHERE rn > 1; DELETE FROM table_name WHERE primary_key IN (SELECT primary_key FROM temp_dupes); Debug-friendly
Subquery DELETE FROM table_name WHERE primary_key NOT IN (SELECT MIN(primary_key) FROM table_name GROUP BY key_column); Risky, less clear
Scenario 4: Hierarchical Data (Recursive CTE)
Approach SQL Example Why / When to Use
Recursive CTE (ONLY OPTION) WITH RECURSIVE hierarchy AS (SELECT id, parent_id, name, 1 AS level FROM table_name WHERE parent_id IS NULL UNION ALL SELECT t.id, t.parent_id, t.name, h.level + 1 FROM table_name t JOIN hierarchy h ON t.parent_id = h.id) SELECT * FROM hierarchy; Org charts, trees
Temporary Table ❌ Not supported Use recursive CTE
Subquery ❌ Not supported Impossible
Scenario 5: Gap Detection (Advanced Analytics)
Approach SQL Example Why / When to Use
CTE + LEAD() WITH gaps AS (SELECT id, value, LEAD(value) OVER (ORDER BY value) AS next_value FROM table_name) SELECT * FROM gaps WHERE next_value - value > 1; Detect missing sequences
Temporary Table CREATE TEMPORARY TABLE temp_gaps AS SELECT id, value, LEAD(value) OVER (...) AS next_value FROM table_name; Heavy analytics
Window Functions ▸

Concepts: ROW_NUMBER, RANK, DENSE_RANK, LAG/LEAD, SUM/AVG OVER, PARTITION BY

When to use: Running totals, ranking, comparing rows within a group.

SELECT
  order_id, customer_id, amount,
  ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY amount DESC) as rank
FROM orders;
💡 Window functions compute without collapsing rows (unlike GROUP BY).

Interview tip: Know ROW_NUMBER vs. RANK — ROW_NUMBER never skips, RANK does with ties.

⚡ PERFORMANCE & OPTIMIZATION

Query Optimization & Indexes ▸

Concepts: EXPLAIN PLAN, indexes, query cost, avoiding full table scans, statistics

Optimization checklist:

✓ Use EXPLAIN to see the query plan
✓ Index on WHERE and JOIN columns
✓ Avoid SELECT *
✓ Filter early with WHERE
✓ Use indexes for ORDER BY
✓ Consider materialized views for repeated aggregations
💡 An index on a WHERE column can reduce a full table scan to milliseconds.

Interview tip: Explain the trade-off: indexes speed up reads but slow down writes.

Data Manipulation: INSERT, UPDATE, DELETE ▸

Concepts: INSERT, UPDATE, DELETE, transactions, rollback safety

Safe update pattern: Always test SELECT before UPDATE/DELETE.

-- Test first:
SELECT * FROM users WHERE status = 'inactive';
-- Then update:
UPDATE users SET status = 'archived' WHERE status = 'inactive';
💡 Use transactions to roll back if something goes wrong: BEGIN; [queries]; ROLLBACK or COMMIT;

Interview tip: Emphasize the importance of WHERE clauses and testing SELECT before mutation.

Best Practices & Common Pitfalls ▸

Key patterns to know:

❌ SELECT * (wasteful)
✓ SELECT specific_column

❌ NOT IN with NULL (returns nothing)
✓ NOT IN only for finite sets, use NOT EXISTS for complex conditions

❌ GROUP BY without ORDER BY for determinism

Interview tip: Talk about NULL handling — COALESCE, NULLIF, and IS NULL vs. = NULL.

Date & Time Functions ▸

Concepts: Date types, date functions, dynamic date ranges, time intervals

Common Date Functions:

NOW() / CURRENT_TIMESTAMP — Current date and time
CURRENT_DATE() — Current date only
DATEPART() / EXTRACT() — Extract specific part (year, month, day)
DATE_ADD() / DATEADD() — Add/subtract intervals
DATE_DIFF() — Calculate difference between dates
DATE_TRUNC() — Truncate to start of period (month, year, etc.)
COALESCE() + date functions — Handle NULL dates

Real-world example - Last 7 days:

SELECT * FROM table
WHERE proc_dt BETWEEN DATEADD(day, -7, CURRENT_DATE()) AND CURRENT_DATE();

Dynamic date ranges: Current month, previous month, current year, YTD, rolling windows

💡 Use DATE_TRUNC to align dates to period boundaries (start of month, start of year), then calculate ranges.

Interview tip: Be ready to handle timezone-aware timestamps and explain INTERVAL vs. DATE_ADD for different databases.

SQL-Focused Data Cleaning ▸

Concepts: Removing duplicates, handling NULL values, standardizing formats, data validation

Why it matters: Data cleaning is 80% of data work. Mastering SQL-based cleaning is faster and more scalable than manual methods.

Interview tip: Explain your approach: identify issues → test the fix → apply → verify. Always test on a subset first.

💡 Never modify production data directly. Always work on a copy and validate results before committing.

🧹 SQL-Focused Data Cleaning Techniques

Technique Description SQL Example
Remove Duplicates Eliminate repeated rows DELETE FROM sales WHERE id IN (SELECT id FROM sales GROUP BY col HAVING COUNT(*) > 1);
Handle Missing Values Fill or remove nulls UPDATE sales SET amount = 0 WHERE amount IS NULL;
Standardize Formats Ensure consistent date, phone, text UPDATE sales SET phone = REGEXP_REPLACE(phone, '[^0-9]', '');
Trim Whitespaces Remove extra spaces from text UPDATE sales SET name = TRIM(name);
Convert Data Types Correct column types ALTER TABLE sales ALTER COLUMN amount TYPE numeric;
Validate Data Enforce business rules DELETE FROM sales WHERE age <= 0;
Remove Irrelevant Columns Drop unnecessary columns ALTER TABLE sales DROP COLUMN temp_column;
Handle Duplicated IDs / Keys Ensure unique primary keys SELECT id, COUNT(*) FROM sales GROUP BY id HAVING COUNT(*) > 1;
Stored Procedures ▸

Concepts: Creating procedures, input/output parameters, conditional logic, transactions, error handling, local vs session variables

What are Stored Procedures? Precompiled sets of SQL statements stored in the database and executed as a single unit. Write once, call many times.

Why Use Stored Procedures?

✓ Performance: Compiled once, reused many times
✓ Reusability: Write once, call many times
✓ Security: Grant users access to procedures, not tables
✓ Maintainability: Centralized business logic in database
✓ Prevents SQL injection (when parameters are used)

📝 Basic Syntax

CREATE PROCEDURE procedure_name
AS
BEGIN
  SELECT * FROM table1;
END;

CALL procedure_name;

🔧 With Input Parameters

CREATE PROCEDURE GetEmployeeByDept
  @Department VARCHAR(50)
AS
BEGIN
  SELECT * FROM Employees
  WHERE department = @Department;
END;

➕ Insert Data Example

CREATE PROCEDURE AddEmployee
  @Name VARCHAR(100),
  @Dept VARCHAR(50),
  @Salary DECIMAL(10,2)
AS
BEGIN
  INSERT INTO Employees (name, department, salary)
  VALUES (@Name, @Dept, @Salary);
END;

❓ With Conditional Logic (IF)

CREATE PROCEDURE CheckSalary
  @Salary DECIMAL(10,2)
AS
BEGIN
  IF @Salary > 50000
    SELECT 'High Salary' AS Status;
  ELSE
    SELECT 'Low Salary' AS Status;
END;

💾 With Transactions

CREATE PROCEDURE TransferSalary
AS
BEGIN
  BEGIN TRANSACTION;
  UPDATE Employees SET salary = salary - 1000 WHERE emp_id = 1;
  UPDATE Employees SET salary = salary + 1000 WHERE emp_id = 2;
  COMMIT;
END;

🛡️ Error Handling (TRY/CATCH)

BEGIN TRY
  -- procedure logic
END TRY
BEGIN CATCH
  SELECT ERROR_MESSAGE();
END CATCH;

📤 Output Parameters

CREATE PROCEDURE SUM_tot
  @col_1 INT,
  @col_2 DECIMAL(9,2) OUTPUT
AS
BEGIN
  SELECT @col_2 = SUM(tot_orders)
  FROM table
  WHERE col = @col_1;
END;

SET @result = 0;
CALL SUM_tot(10, @result OUTPUT);

Triggers & Events ▸

Concepts: Triggers (BEFORE/AFTER INSERT/UPDATE/DELETE), Events (scheduled tasks), automation, auditing, maintenance

Key Idea: Triggers run on data changes; Events run on schedules. Both automate database tasks.

🎯 Trigger Basics

What activates a trigger: INSERT, UPDATE, or DELETE on a specific table

Timing: BEFORE or AFTER the operation

Scope: Bound to one table, fires per row or per statement

Use cases: Enforcing business rules, auditing changes, validating data, maintaining summary tables

Example: Auto-set timestamp on insert
CREATE TRIGGER before_insert_user
BEFORE INSERT ON users
FOR EACH ROW
BEGIN
  SET NEW.created_at = NOW();
END;

⏱️ Event Basics

What activates an event: A specific time or recurring schedule

Timing: Executes when schedule fires, independent of user queries

Scope: Not tied to a table, runs in background

Use cases: Periodic cleanup, scheduled reports, archiving data, maintenance tasks

Example: Daily cleanup of old logs
CREATE EVENT cleanup_old_logs
ON SCHEDULE EVERY 1 DAY
DO
  DELETE FROM logs WHERE created_at < NOW() - INTERVAL 30 DAY;

🔄 Trigger vs Event Comparison

Feature Trigger Event
Activated by Data change (INSERT/UPDATE/DELETE) Time / schedule
Runs Immediately on DML On schedule
Tied to table ✅ Yes ❌ No
Frequency Per row / per statement Once or recurring
User action required ✅ Yes (DML operation) ❌ No (background)
Typical use Data integrity, auditing Maintenance, batch jobs

📋 When to Use Which

Use a TRIGGER when:

✓ Logic must run whenever data changes
✓ You need to enforce rules automatically
✓ You need real-time auditing or validation
✓ Example: Update an "updated_at" timestamp on every change

Use an EVENT when:

✓ Logic must run at a specific time
✓ You need recurring background jobs
✓ No user action should trigger the work
✓ Example: Delete expired sessions every hour

🔧 Managing Triggers & Events

View all triggers:
SHOW TRIGGERS;

Drop a trigger:
DROP TRIGGER IF EXISTS trigger_name;

Enable event scheduler (MySQL):
SET event_scheduler = 'ON';

View event status:
SHOW VARIABLES LIKE 'event%';

⚠️ Best Practices

Practice Details
✔ Keep triggers simple & fast Avoid heavy logic; triggers block DML operations
⚠ Avoid long transactions in triggers Can lock tables and cause performance issues
✔ Use events for batch work Let events handle bulk operations off-hours
⚠ Enable event scheduler Events won't run if event_scheduler is OFF
✔ Document trigger logic Hidden logic in triggers can confuse developers
💡 Triggers are powerful but can make debugging hard — hidden logic fires automatically. Use them for critical business rules only, and always document what they do.

Interview tip: Explain use cases clearly: when data changes (trigger) vs when time matters (event). Know the performance implications of triggers on high-volume tables.

View Type Storage Performance Use Case
Standard View (Logical) Query definition only Re-evaluated on each query; slower with complex joins Temporary abstractions, simplified queries, security (row/column masking)
Materialized View Actual cached data on disk Very fast; only updates when refreshed High-volume queries, heavy aggregations, time-series data
Dynamic Table Incrementally maintained cache Near real-time updates; faster than standard views Fresh analytics, dashboards, event-driven updates (Snowflake-specific)
Iceberg Table Versioned data format Fast time-travel and partition pruning Data lakes, versioning, compliance, ACID transactions (Snowflake-specific)
Temp View Session-only definition Same as standard view; isolated to session Debugging, intermediate calculations, session-scoped logic
Secure View Encrypted query definition Slight overhead for security checks PII masking, role-based access, secure data sharing

💡 When to Use Each Snowflake View

Scenario Best Choice Why
Real-time dashboard query Dynamic Table or Materialized View Need fresh data without re-computing joins every time
Complex transformation layer Materialized View (if stable) / Dynamic Table (if changing) Avoid re-computing expensive joins on each query
Simple SELECT wrapper (no joins) Standard View Minimal overhead; clean abstraction
Data masking / security Secure View Hide definition from unauthorized users
Audit trail / versioning Iceberg Table Time-travel and full change history
Temporary debugging / ETL Temp View Session-scoped; auto-cleanup
